# Dashboard compute (initial prototype)

The test configuration samples Jobs whose name starts with `metrology-processor-` every minute. The metrology CronJob requests 500m CPU (0.5 cores), not 1 mCPU; its limits are 2 cores and 8 GiB. Requests and limits are not actual consumption. Each metrics response averages CPU over its own reported window, usually much shorter than a minute. Only that window is integrated into core-hours and GiB-hours; time between windows and unsampled jobs is missing. A one-minute CronJob may also start late or miss a run. This is a lower-coverage estimate, not reliable billing or an invoice. Observed seconds are summed across pods and can exceed wall-clock time. Overlapping API windows may double count, and windows crossing midnight are assigned to the end date. Review coverage and validate attribution before using these figures for billing.

The source-neutral `UsageRecord` stores source, external ID, group, interval and CPU/RAM/disk quantities in core-hours and GiB-hours. Nullable disk fields reserve space for future data; Kubernetes does not populate them. A future CSV adapter can write records under a separate stable source and unique external ID, but no CSV importer is implemented. Rate records are source-specific and effective-dated. Once rates are agreed, a privileged operator can run `manage.py set_compute_rate kubernetes:core-omero-test 2026-01-01T00:00:00Z SEK 1.0000 1.0000` with actual approved values; optional `--disk` sets a disk rate. The example numbers are placeholders. No rates are installed by default. Rate changes inside a measurement interval leave it unpriced. Changes to historical rates affect displayed estimates; they are not immutable invoices.

This module samples CPU and memory for pods in one Kubernetes namespace. It is an initial implementation, not deployed or production ready. It requires an existing `metrics.k8s.io` implementation and adds no cluster monitoring software. The module runs inside the dashboard and exposes a staff/admin-only page and overview card. The collector runs separately using the dashboard database.

## Meaning and limitations

CPU is the sum of container CPU usage in nanocores, averaged over the metrics API's reported window; memory is the sum of container working sets in bytes. These are samples, not total CPU time or a complete account of short-lived jobs. They do not measure host processes or total node utilization. The pod UID, namespace, node name and direct Job owner are recorded where available. The pod label `dashboard.cci.gu.se/omero-group` is copied as an unverified group identifier; absent or empty labels default to `CCI`. It is not a verified OMERO group mapping or an authorization mechanism. Label values should be controlled by trusted workload submitters; group names and IDs need an agreed mapping before billing or researcher access. A shared node must not be attributed to one group merely because it runs a group's job.

The Metrics API has no disk usage. Kubelet `/stats/summary` can provide node filesystem and some ephemeral storage data, but its node proxy permission is sensitive and unavailable to the account checked. Persistent volume usage is a separate measurement and cannot be inferred from node disk usage. Ask IT whether an existing monitoring API can expose appropriate disk metrics; no disk value is stored or inferred here. Node capacity or utilization also requires separate cluster-scoped permissions and source validation.

## Setup and scheduling

For local development install this package in the dashboard environment, enable `dashboard_compute` in `INSTALLED_APPS` and register `dashboard_compute.dashboard_module.module` in `DASHBOARD_MODULES` as described in the core's `MODULE_CONTRACT.md`. Run `manage.py migrate` with a setup identity. Package registration and a pinned release in the core are still needed before deployment; this checkout alone is not included in the core image. Apply neither example manifest without adapting and reviewing it with IT. The collector needs `list` on pods and pod metrics in its namespace, database insert access and the dashboard settings/secrets. The web process needs read access. Migration privileges should remain separate. Deploy one collector per namespace and database; each run lists all visible pods, so use a dedicated scope if workloads are sensitive. The example CronJob runs every minute with overlap forbidden. API errors fail the job; monitor failures and gaps. A pod that disappears between the pod and metrics lists is skipped.

The database tables are `dashboard_compute_podsnapshot`, `dashboard_compute_usagerecord` and `dashboard_compute_rate`. Unique identities prevent duplicate sample inserts. Timestamps come from the metrics API, not the CronJob. Include all tables and indexes in normal dashboard backups. Retention and aggregation are not automated yet: deleting raw data without an agreed retention policy would be irreversible. At one-minute intervals expect up to 525,600 snapshots and as many usage rows per continuously running pod per year. Before production, agree retention and implement rollups with counts and coverage, then test recovery and PostgreSQL 15 migrations. Aggregation reduces row count; database compression alone does not.

## Access investigation (test project)

On 2026-11-23, account `xlecsi` in `core-omero-test` could list namespace pods and pod metrics according to `oc auth can-i`; it could not list nodes or use node proxy. A direct cluster-wide node metrics request returned Forbidden. The collector service account is distinct and must be tested separately. Authorization checks alone do not prove metrics are present or usable.
